# BUG-012: リネームを別の行のクリックで確定すると、その行が選択されない

- **State**: Fixed
- **Reported**: 2026-07-30
- **Area**: file-list / rename（`src/ExtendExprorer/Views/FileListView.xaml.cs`）

## Summary

インラインリネーム中に別のファイル行をクリックすると、リネームは正しく確定して編集ボックスも閉じるが、
クリックした行が選択されず、選択が空になる。

## Reproduction

1. ファイルを 1 つリネーム編集中にする
2. 名前を変更したうえで、別のファイル行をクリックする
3. リネームは確定する（ディスクにも反映される）が、クリックした行は選択されていない

## Expected

リネームが確定し、かつクリックした行が選択される（エクスプローラーと同じ）。

## Cause

`FileListView.OnSelectionChanged` の「再読込中は選択変更を無視する」ガードが、ユーザーの選択まで
落としていた。

`ListView` は選択の移動を **2 回の `SelectionChanged`**（旧項目の解除 → 新項目の選択）で通知する。

1. 1 回目（選択が空になる）: `_renamingEntry` から選択が外れたと判断して `CommitRename` を実行。
   確定処理が `RefreshAsync()` を呼ぶため、この時点で `IsLoading` が true になる。
   同時に「覚えている選択（`_selectedNames`）」も空になる。
2. 2 回目（新しい行が選択される）: すでに `IsLoading == true` なので
   `if (_restoringSelection || _viewModel?.IsLoading == true) return;` に吸われ、
   **`_selectedNames` が更新されない**。
3. 再読込完了後、`_selectedNames`（空）から選択を復元するため、選択が空のままになる。

`IsLoading` のガードは「`Entries` を作り直す際の一時的な選択解除を無視する」ためのもので、
選択が増える方向の通知まで無視する必要はなかった。

## Fix

ガードを「再読込中の**空になる**通知だけ無視する」に絞った。

```csharp
if (_restoringSelection) return;
// 作り直しに伴う一時的な解除（選択が空になる通知）だけ無視する。
// 選択が入る通知は、再読込中でもユーザーの操作なので記録する
if (_viewModel?.IsLoading == true && List.SelectedItems.Count == 0) return;
```

`Entries` の作り直しでは選択は空になる方向にしか動かないため、従来の目的は保たれる。
