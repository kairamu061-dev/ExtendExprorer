# file-list 開発メモ

## 実装上の判断

<!-- なぜその実装にしたかを記述する -->

| 判断内容 | 理由 |
|----------|------|
| インライン リネームの起動判定を「タップ完了時点の単独選択項目を候補として覚える」方式にした（2026-07-20・BUG-006） | `PointerPressed` 時点では選択がまだ更新されておらず、「選択済み項目の再クリック」を安定して判定できなかった |
| 編集中フラグ `_renamingEntry` を単一の真実とし、`CommitRename` は `box.DataContext` を信用しない（2026-07-25・BUG-007） | ListView のコンテナ再利用で DataContext が別項目に差し替わると、後始末が走らず編集状態が残り続けるため |
| 一覧の更新をイベント駆動（`FileSystemWatcher`）にした（2026-07-25・BUG-008） | シェル操作は非同期完了で、移動元ペインには通知が来ない。操作直後の一度きりの再読込では取りこぼす |
| 自動再読込のデバウンスは 400ms（2026-07-25） | 1 操作で数十件の通知がバーストで届くため。体感で「すぐ反映」と感じる範囲の上限として選択 |
| セッション保存の起点を `Navigated` から `PathChanged` に分けた（2026-07-25） | 自動再読込のたびに保存すると、`%LOCALAPPDATA%\ExtendExprorer` 表示時に「保存→変更通知→保存」が回り続ける |
| 選択の維持は「名前で覚えて復元」方式（2026-07-25） | `Entries` を作り直すと ListView の選択は必ず解除される。差分更新は大量ファイル時に O(n^2) になりやすく、名前復元の方が単純で安全 |
| 選択色・編集ボックスは ThemeResource の局所上書きで対応（2026-07-25） | ControlTemplate をコピーすると WinUI 更新に追従できなくなる。必要なブラシ・寸法だけ差し替える |

## 発生した問題と対処

<!-- 詰まった点・解決方法を記述する -->

| 問題 | 対処 |
|------|------|
| 移動を挟むとインラインリネームが一切開始しなくなる（BUG-007） | `TabViewModel.Navigated` を購読して移動のたびにリネーム状態をリセット。同一タブ内の移動では `ViewModel` セッターが呼ばれないことが盲点だった |
| 選択復元中の `SelectionChanged` が復元途中の状態で記憶を上書きし、1 件しか復元されない | `_restoringSelection` フラグで復元中の通知を無視する |
| 一覧に「Ctrl+C」ツールチップが出る（BUG-009） | `KeyboardAccelerator` の既定キーヒント。`KeyboardAcceleratorPlacementMode="Hidden"` で抑止 |

## 設計からの変更点

<!-- 設計書との差分と理由を記述する -->

| 変更内容 | 理由 |
|----------|------|
| `TabViewModel` が `IDisposable` になった | フォルダ監視のハンドル・スレッドをタブ/ペインのクローズで解放するため（BUG-002 と同じ趣旨） |
| `IsLoading` を `Entries` 差し替えの後に落とすようにした | ビューが「再読込に伴う一時的な選択解除」を判別できるようにするため |

## 今後の課題

<!-- 現状の制限・将来対応すべき事項を記述する -->

- 自動再読込は表示中フォルダのみ（サブフォルダは監視しない）。ツリー側の自動更新は未対応
- 巨大フォルダ（数万件）での自動再読込コストは未実測。必要なら差分更新へ切り替える
- F2 キーでのリネーム開始は未対応（要望が出れば追加）
