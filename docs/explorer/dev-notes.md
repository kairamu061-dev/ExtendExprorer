## 実装上の判断

<!-- なぜその実装にしたかを記述する -->

| 判断内容 | 理由 |
|----------|------|
| 技術スタックを Electron から WinUI 3 (C#/.NET 8) に変更（2026-07-04） | ユーザ方針「動作の軽さとメモリ使用量の節約」。Tauri / Wails / WinUI 3 / Electron を比較提示し、ユーザが WinUI 3 を選択 |
| タブ UI に WinUI 標準 TabView を採用 | 追加ボタン「＋」・クローズ・ホイールクリックを標準装備し、自前実装より軽くて確実 |
| 配布は当面 unpackaged（MSIX 化は将来検討） | 開発初期の反復を優先。パッケージングは配布段階で判断 |
| DI コンテナを使わず App.OnLaunched の合成ルートで手動注入（2026-07-05） | 現状サービス 2 つ程度でコンテナは過剰。増えたら Microsoft.Extensions.DependencyInjection 導入を再検討 |
| ツールバーに暫定のパス表示 TextBlock を設置（2026-07-05） | file-list 単体の動作確認に現在位置の表示が必要なため。address-bar 実装時に置き換える |
| 隠し・システム属性は Opacity 0.55 の減光で薄灰色表現（2026-07-05） | ユーザ要望「常時表示のまま色だけ変えたい」。テーマ（ライト/ダーク）どちらでも自然に沈むため固定色でなく不透明度を採用 |
| ソート状態はフォルダ移動で既定（名前昇順）にリセット（2026-07-05） | ユーザ要望。タブ複製時のソート引き継ぎも「しない」で統一（フォルダ単位の一時状態と定義） |
| CI に Native AOT ビルドを実験追加（2026-07-05） | メモリ使用量削減の検証。通常ビルド（147MB 起動時）に対する効果を実測で判断し、良ければ AOT を正式採用 |
| Native AOT を正式ビルドに昇格（2026-07-08 検証合格を受け 2026-07-11 入替） | BUG-001 解消確認済み。起動時メモリ 141.2→111.9MB（約21%減）・配布 zip 63→31MB。成果物名: `ExtendExprorer-win-x64`=AOT、`-jit`=切り分け用フォールバック |
| 見た目の調整は ControlTemplate を差し替えず ThemeResource の局所上書きで行う（2026-07-25） | テンプレートをコピーすると WinUI/Windows App SDK の更新に追従できなくなる。タブ帯の縮小・選択色・リネーム編集ボックスはいずれも寸法とブラシの上書きだけで足りた |
| 行の高さは `Height` 固定ではなく `MinHeight` で与える（2026-07-27） | 固定すると日本語のラベル（タブ名・フォルダ名）が下に見切れる。`MinHeight` なら内容に合わせて必要なだけ伸びるので、詰まり具合を保ったまま見切れを防げる |
| ツールバーのアイコンは当面 Segoe Fluent Icons のグリフ、最終的に生成アイコンへ差し替え（2026-07-27） | アイコン到着を待たずに「全ボタンがアイコン表示」の状態を先に作れる。差し替えは `FontIcon` → `Image` の置換のみ |
| ツリー幅は「View が持ち、MainWindow が session に付け足す」形にした（2026-07-30） | 幅・折りたたみはレイアウト木（MainViewModel）と無関係な View 固有の状態。`Bounds` と同じ扱いにすることで MainViewModel を UI 寸法から切り離したままにできる |
| ツリーの幅調整に `SplitterBar` を再利用せず `PanelSplitter` を新設（2026-07-30） | `SplitterBar` は `SplitNodeViewModel.Ratio`（比率）を前提にしており、固定幅 px を動かす用途とは扱う値が違う。共有できるのはカーソルだけなので `SplitterCursors` に切り出した |
| 名前のソートを `StrCmpLogicalW`（自然順）に変更（2026-07-30・コードレビュー指摘 2） | `CurrentCultureIgnoreCase` では `File10` が `File2` より前に並び、エクスプローラーと順序が違っていた。「見た目・操作感をエクスプローラーに寄せる」方針に直結する差分なので採用。AOT 互換の `LibraryImport` で追加コストもない |
| フォルダ監視は「項目の増減」と「内容の変化」で待ち方を分ける（2026-07-30・コードレビュー指摘 3） | 増減・改名は最初の通知から 400ms で必ず反映（見えないと困る）。サイズ・更新日時の変化は落ち着くまで期限を延ばす（大きなファイルの書き込み中に再読込が走り続けるのを防ぐ） |
| シェルアイコンのキャッシュは成功だけを保持する（2026-07-30・BUG-010） | 失敗した Task を残すと、`<dir>` キーを共有している全フォルダが一度の失敗で恒久的にグリフ表示へ落ちる。リトライ抑止は VM 単位の `_iconRequested` で足りる |
| アイコンは `IconSource` ではなく 16x16 の `Grid`（グリフ＋`Image`）で統一（2026-07-30・BUG-011） | `ImageIconSource` は固有サイズを持たず、寸法を与えない親（`TabViewItem`）の下では測定が無限大になり表示されない。一覧・ツリー・タブで同じ作りに揃えた |
| 受領した生成アイコンは、そのまま使わず「内容のバウンディングボックス基準」で正規化してから取り込む（2026-07-27） | 生成物は素材ごとに描画サイズが 564〜798px とばらついており、そのまま縮小するとツールバー上で大きさが不揃いに見える。矢印 30/32・四角 26/32 に揃えた（四角は面積が大きく見えるため小さめ） |
| 矢印はアウトラインをやめてソリッドにする（2026-07-30） | 生成素材は輪郭線だけで内側がほぼ透明（アルファ 10 前後）。16px では線が潰れて Segoe グリフと区別が付かず「文字のまま」に見えた。輪郭の内側を塗ってシルエットにすると、同じ絵柄のままアイコンとして読める |
| 幾何学的なアイコン（分割）は生成素材を使わず自前で描く（2026-07-30） | 16px 表示で線がピクセル境界に乗らずにじみ、左右・上下の間隔が不揃いに見えていた。2:1 縮小で 1px に落ちるよう偶数座標・偶数太さで描けば、縦横で完全に同じ寸法を保証できる。単純な図形なら生成に頼るより確実 |
| 一覧の追随は「全体の読み直し」ではなく差分更新にする（2026-08-04） | 読み直すと並べ替えが走り、追加・リネームのたびに行が動いて落ち着かない。追加＝末尾／リネーム＝位置固定は参考ツール（Tablacus）と同じ挙動で、ユーザーの期待に合う。並べ替えは列ヘッダのクリックという明示操作に限定する |
| フォルダ監視は項目の増減・改名だけを見る（2026-08-04） | サイズ・更新日時まで見ると、ホームのように常時書き込みのあるフォルダで更新が止まらない。列の値が古くなるのは移動・再読込で解消するので実害が小さい |
| バインド評価中に PropertyChanged を発火させない（2026-08-04・BUG-013） | `Icon` の getter は XAML のバインド評価から呼ばれる。キャッシュヒットで Task が同期完了すると、その場で通知が飛んでバインドへ再入する。タイミング依存で JIT では出にくく、AOT の起動クラッシュとして現れた疑いが強い。非同期完了を保証して回避した |
| 16〜20px の UI アイコンはラスタでなくベクター（XAML の Path / Ellipse / Rectangle）で描く（2026-08-01） | 生成 AI のラスタは 512/1024px が native で、小さいサイズを直接出力できない＝必ず縮小が要る。縮小するかぎり、にじみ・DPI ごとの作り直し・細い線の消失が付いて回る。ベクターなら描画時に実解像度でラスタライズされるため縮小が発生せず、色をブラシで持てるのでダークテーマ用の白版アイコンも不要になる。**大きく作って縮小する方式が正しいのはアプリアイコン（.ico）だけ**で、あちらは仕様上 16〜256px を 1 ファイルに持つ必要がある |
| 幾何学的なアイコンは座標調整でなく「中央揃えの矩形」で組む（2026-08-01） | 枠と仕切りを `HorizontalAlignment=Center` で重ねれば、左右・上下の間隔は構造的に等しくなる。座標を手で合わせる方式は、素材やサイズが変わるたびに崩れる |
| ラスタのアイコンは「表示サイズの整数倍」で作り、縮小がピクセル境界に乗るようにする（2026-08-01） | 40px の枠に 38px の円を置いた（1px ずれ）だけで、20px 表示時に縁が半画素にまたがって全体がにじむ（20px 化したときの端のアルファが 116＝半分だけ塗られた状態になる）。枠を完全に埋めれば 246〜255 になり、2:1 の縮小がそのまま乗る |
| 大きな縮小率は一気にかけず段階的に落とす（2026-08-01） | 256px→40px を 1 回の LANCZOS で落とすと細い線が溶ける。半分ずつ reduce してから目標サイズにし、最後に軽いアンシャープをかけると輪郭が戻る。アプリアイコンの各サイズも同様 |
| アプリアイコンはサイズごとに絵を変える（2026-07-30） | 16〜48px では中心の分割パネルの細部が潰れてノイズにしか見えない。小サイズは面を大きく取った簡略マーク、64px 以上は元の絵、という .ico のマルチサイズ本来の使い方にした。占有率も 76%→96% に広げ、他アプリのアイコンと並んだときに小さく見えないようにした |
| アイコンは 32px の PNG 1 枚を 16px 表示で使う（2026-07-27） | 100% DPI では 1/2 縮小、200% DPI では等倍で描かれる。`.scale-100/200` の修飾子付きリソースは unpackaged 配布での解決に不確実さがあるため避けた |
| 生成アイコンの背面に Segoe グリフを残し `ImageFailed` で切り替える（2026-07-27） | unpackaged 配布での `ms-appx` 解決が実機で確認できていないため。読めなくてもボタンが空にならない |
| メモリ目標を満たす UI 基盤を、見積もりでなく実測スパイクで選ぶ（2026-08-12） | 目標が 30MB 前後に格上げされ、WinUI 3（雛形で 114MB）では届かないことが確定した。移行先の候補（C# + 素の Win32 / C# + WinForms / C++ + Win32）はどれも「予測 20〜80MB」と幅があり、見積もりで全面書き直しを決めると外したときの損失が大きい。AOT 採用時と同じく、同じものを表示する最小スパイクを CI で作って実測してから決める。**最大の分岐は「C# のまま XAML を捨てて 30MB 台に入るか」**で、入るなら書き直しは UI 層だけで済み、ViewModel 層・シェル連携がそのまま残る |
| スパイクではアイコンを OS のシステムイメージリストから借りる（2026-08-12） | 本体は 1 枚ずつ `WriteableBitmap` に変換して抱えているが、Win32 の ListView は画像の実体を OS 側に置いたまま**項目ごとにインデックス（int）だけ**を持てる。参考ツールが軽い理由の 1 つで、スパイクでもここは同じ条件に揃えないと比較にならない |
| 一覧の更新をイベント駆動（`FileSystemWatcher`）に統一（2026-07-25・BUG-008） | 操作ごとに `RefreshAsync` を呼ぶ方式では、シェル操作の非同期完了と「移動元ペインには通知が来ない」ケースを取りこぼす。監視なら外部アプリによる変更も同じ経路で拾える |

| 同じハンドラを `PreviewKeyDown` と `KeyDown` の両方に登録し、Tab 1 回で 2 回実行させた（2026-08-13） | `handledEventsToo` で登録すると `Handled` にしても後段は止まらない。**「効く方だけ動くはず」の保険は、両方効くと二重発火になる**。しかもハンドラが自分で状態（`_renamingEntry`）を作り直す作りだったため、2 回目の条件も成立して症状が分かりにくくなった。**保険で複数経路に登録しない**（どちらが効くか分からないなら、まず 1 つで実測する） |
| 行を詰める変更で `TreeViewItem` に `Height` を固定し、アイコンと文字を 7px に潰した（BUG-014） | `ContentControl` の高さを固定すると中身がその枠に押し込められる。**行高は `MinHeight` で与える**（`ListViewItem` と同じ）。検証も行ピッチだけでなく**行の中身の高さ**を見る（実装・検証の両方が 2 回続けて見逃した） |

## 今後の課題

<!-- 現状の制限・将来対応すべき事項を記述する -->

- タブごとの履歴（戻る/進む）はセッション復元対象外（初期版はパスのみ）
- folder-tree は自動更新の対象外（表示中フォルダのみ監視。ツリー側は再展開で反映）
- 配色のダーク OS 下での固定確認は未実施（検証環境がライトテーマのため持ち越し）
- シェル操作（コピー/移動/削除/クリップボード）が失敗しても無反応になる。シェルがダイアログを出さない失敗（クリップボードのロック等）はユーザーに伝わらない → ロギングまたは軽い通知の検討（コードレビュー指摘 1）
- シェルアイコン取得が一時的に失敗する引き金は未特定（BUG-010 は「失敗しても自己回復する」ようにして影響を止めた段階）
- 初回起動時にウィンドウ表示直後にプロセスが静かに終了する事象が 1 度だけ報告されている（ダンプ・WER 無し／以降は再現せず・2026-07-30）。再発したら初回起動限定の条件を調べる
- 大量ファイル（1 万件超）時の性能は仮想化 ListView で見込みだが、実測は未実施
- メモリ使用量の計測基準（起動直後/System32 後）: 雛形 114MB → file-list 147/182MB → tabs 142.6/200.9MB(タブ操作後) → **AOT 正式採用後 111.9/157.7MB**（2026-07-08 計測）。**2026-08-12 に目標が「30MB 前後」の要件へ格上げされたため、111.9MB は基準ではなくなった**
  （WinUI 3 では到達できず、UI 基盤の載せ替えを決定。`docs/win32-migration/` 参照）
- **参考ツールの比較値を訂正（2026-08-12）**: 従来「Tablacus 約 75MB」と記録していたが、
  ユーザ実測で**複数タブ・複数エリアの起動直後で 29MB**。**差は約 1.5 倍ではなく約 3.9 倍**。
  75MB がどの条件の値だったかは不明のため破棄する。以後の比較基準は **29MB**。
  なお 29MB は「タブ・エリアを増やした状態」の値で、Tablacus 側はタブ数を増やしても
  ほとんど増えないことを意味する
- タブクローズ後のメモリ回復（リーク有無）の長時間シナリオ計測は未実施（検証セッションが次回以降に予定）
- ユニットテストプロジェクトが未整備（初期版は手動 E2E のみ。ViewModel はサービス注入で分離済みのため導入は容易）

|---|---|---|
| 別のフォルダへ移動 | いいえ | **先頭** |
| 読み直し（`F5`・監視） | **はい** | **動かさない** |
| **並べ替え** | **はい** | ★ **選択が見える位置** |

**後ろ 2 つは「引き継ぐ」が同じで、「見せる場所」が違う。**
bool では表せないので、**並べ替えのときに選んだ行が画面から外れていた。**

`ResetKind`（`Navigate` / `Reload` / `Reorder`）に差し替えた。

> **3 回とも形が同じだった。**
> 「true/false で足りている」と見えるのは、**まだ 2 つ目の問いが来ていないだけ。**
>
> **見分け方**: その bool の名前が**答えの名前**になっているか
> （`keepSelection`＝「選択を引き継ぐか」）、
> それとも**場合の名前**になっているか（`ResetKind.Reorder`＝「並べ替えた」）。
> **答えの名前は 1 つの問いにしか使えない。場合の名前なら、問いを後から足せる。**

**自動テストは「どの種類が飛ぶか」で固定した。**
受け取る側（画面の送り方）は実機でしか見えないが、
**種類の割り当てが間違っていれば CI で落ちる。**

## 2026-10-25: 「何もしない」は、何もしなければ実現しない（BUG-053）

BUG-052 で `ResetKind` を分けて**「`Reload` では位置を動かさない」と決めた。**
**決めただけで、何もしていなかった**——`Reload` の枝は空だった。

渡していないので、コモンコントロールが**焦点のある行**を見える位置まで送っていた。

### 旗を 2 つに分けた

`SetItemCount` は `LVSICF_NOINVALIDATEALL | LVSICF_NOSCROLL` を**まとめて**渡すか
**両方渡さない**かの 2 択だった。欲しかったのは **`NOSCROLL` だけ**。

- **`NOSCROLL`**＝位置を動かすな
- **`NOINVALIDATEALL`**＝描き直すな（**画素が古いまま残る**側の危険・BUG-037 の家族）

**この 2 つは別の話**なので、旗を別々に渡せる形にした。
**まとめてあったから「どちらも要らない」を選んでいた**という形で、
これも**1 つの値に 2 つの意味**の家族。

### 旗で押さえた分の面倒は自分で見る

`NOSCROLL` を付けると、**フォルダが縮んだ読み直し**で
「行数より後ろを見ている」状態が残りうる。
`LVM_GETTOPINDEX` で見て、後ろなら先頭へ戻すようにした。

> **自動で面倒を見てくれていたものを止めたら、その面倒は自分のものになる。**
