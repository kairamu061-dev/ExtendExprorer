# BUG-054: 見ているフォルダが外で差し替えられると、増減を拾わなくなる（`F5` でも戻らない）

- **State**: Fixed
- **Reported**: 2026-10-26（検証セッション・§3.2。**依頼書に無い発見**）
- **Area**: `ViewModels/FileListViewModel.StartWatching`

## Summary

見ているフォルダが**外で丸ごと差し替えられる**（`S` → `S_gone` に改名し、別のフォルダを `S` に改名）と、
**そのあとの増減をいっさい拾わなくなる。`F5` を押しても戻らない。**

**別のフォルダへ移って戻るまで直らない。**

## Reproduction

1. `S`（2001 件）を開く
2. 外で `S` を `S_gone` に改名し、別に用意した 30 件のフォルダを `S` に改名する
3. **監視は反応しない**（2.5 秒待っても件数が変わらず、診断にも何も出ない）
4. `F5` を押す → 件数は 30 になる（読み直しは効く）
5. ★ **そのあと外で 1 件足す／消す → 一覧は変わらない**
6. ★ **`F5` を押しても、その後の増減も拾わない**
7. 別のフォルダへ移って戻る → **また拾うようになる**

## Expected

**`F5` を押したら、監視も効くようになる。**

## Measured / Inferred

| | 測った（根拠） | 推測（何が分かれば決まるか） |
|---|---|---|
| 症状 | ★ **検証セッションが実測**（2026-10-26）。各操作のあと 2 秒待って件数を読んでいる。**新旧とも同じ** | — |
| 原因 | ★ **ソースから確定。**`StartWatching` に「**同じフォルダなら使い回す**」があり、**パスの文字列で判定**していた。改名で死んだ監視も、パスが同じなので使い回されていた | **`FileSystemWatcher` が改名の先に付いていくのか、黙って止まるのか**は**確かめていない**（`S_gone` の増減も表示に出ないので、どちらでも説明がつく）。直すのに要らない |
| 影響 | ★ **新旧同一＝前からある。**「一時フォルダに作ってから差し替える」道具（ビルドの出力先・同期ソフト・展開ツール）で起きる | **どのくらいの頻度で踏むか**は分からない |

## Cause

**「同じフォルダか」を、パスの文字列だけで決めていた。**

```csharp
// 再読込のたびに張り替えると、その隙間の変更を取りこぼす。同じフォルダなら使い回す
if (_watcher is { } current && string.Equals(current.Path, path, ...)) return;
```

**使い回す理由は正しかった**（張り替えると隙間の変更を取りこぼす）。
**その判定に使った「同じパスか」が、「同じ生きている監視か」を答えられなかった。**

> **また「1 つの比較で 2 つの問いに答えようとした」形。**
> `isReload`（BUG-040）・`Path`（BUG-048）・`keepSelection`（BUG-052）に続いて 4 度目。

## Fix

**明示的な読み直し（`F5`・監視からの全体読み直し）では、同じパスでも張り替える。**

`StartWatching(path, rearm: isReload)`。`isReload` は既に `Apply` まで渡っている。

★ **張り替えると隙間の変更を取りこぼす**——これが使い回す理由だった。
ただし**列挙そのものが張る前に済んでいる**ので、**隙間は元から在る。**
**死んだ監視を抱え続ける方が重い**と判断した。

張り替えたときは `[watch] 張り替える <path>` を残す（走ったことが分かるように）。

- 修正コミット: **`0ec4a47`**（CI run 40217450092）
- 手順: `docs/explorer/test-cases.md` **E-160〜E-163**

## 残っている範囲

**差し替えの瞬間に監視が反応しないこと自体は直していない**（手順 3）。
**`F5` を押せば直る**ところまで。

**「差し替えを検知する」のは別の話**で、親フォルダを監視する等の作りが要る。
**そこまでするかは、踏んだ数を見てから。**
