# BUG-017: 一覧の選択が行番号で追従し、削除で別のファイルに移る

- **State**: Fixed
- **Reported**: 2026-08-15
- **Area**: win32-migration / file-list（`src/ExtendExprorer.Win32/UI/FileListView.cs`）

## Summary

表示中フォルダの項目が外部で削除されると、選択していたファイルの選択が外れ、
**繰り上がってきた別のファイル**が選択された状態になる。

## Reproduction

1. `f1`〜`f6` のあるフォルダを開く
2. `f2`（行番号 1）と `f5`（行番号 4）を選択する
3. 別のウィンドウから `f2` を削除する
4. 観測: 選択は `f3` と `f6`（行番号 1 と 4 のまま）

## Expected

残るのは `f5` の選択だけ（新しい行番号 3）。

## Cause

オーナーデータ（`LVS_OWNERDATA`）の一覧は選択を**行番号**で持つ。行が動く操作の前後で
名前を控えて付け直す処理は入れていたが、**控えるタイミングが遅かった**。

`FileListViewModel` は `_entries` を書き換えてから `EntryRemoved` / `EntriesReset` を発火していた。
ビューはそれを受けてから `LVM_GETNEXTITEM` で選択行を読むため、

- 一覧（コントロール）が返す行番号 … **古い**並び
- `_model.Entries[index]` … **新しい**並び

を突き合わせることになり、控えた名前が最初から別のファイルのものになっていた。
削除で 1 つ繰り上がるため、控えた名前＝繰り上がってきたファイルの名前になり、
「その名前を選択し直す」ことで報告どおりの結果になる。

## Fix

一覧を書き換える**直前**に発火する `EntriesChanging` イベントを追加し、ビューはそこで
選択名を控えるようにした（`_selectionSnapshot`）。この時点ではコントロールとモデルの
並びが一致しているため、控えた名前が正しい。

発火箇所は行番号がずれうる 3 か所（読み込みの適用・並べ替え・削除）。
追加（末尾）とリネーム（位置固定）は行番号が動かないので不要。

- **Fix commit**: 4d78c2f

## Notes

同じ取り違えは並べ替えでも起きていた（選択したまま列ヘッダをクリックすると別の行が選択される）。
報告では M-17 が合格になっているが、選択のない状態での確認だったため表面化していない。
