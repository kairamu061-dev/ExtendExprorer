# BUG-029: ドラッグ中にプロセスが落ちる（0xc0000409・記録は残らない）

- **State**: Closed（2026-09-02 実機確認）
- **Reported**: 2026-08-30
- **Area**: win32-migration / drag-drop / `src/ExtendExprorer.Win32/UI/ListDropTarget.cs`

## Summary

エクスプローラーからファイルをドラッグしてアプリのウィンドウに入れると、
**ドロップする前にプロセスが消える**。`DragEnter` と最初の `DragOver` は成立していて
（ドロップ効果の「＋ コピー」が出る）、**2 回目のマウス移動で落ちる**。

`error.log` は 1 行も出ない。

## Reproduction

1. アプリと、別フォルダのエクスプローラーを並べる
2. エクスプローラーでファイルを 1 つ掴み、アプリの一覧の上へ持っていく
3. **アプリの上で 2 回ほどマウスを動かす** → 落ちる（ドロップは不要）

| 段階 | 生存 |
|---|---|
| ウィンドウに入る（`DragEnter`） | ○ |
| 入った位置で止まる（最初の `DragOver`） | ○ |
| そこから 1 回目の移動 | ○ |
| **2 回目の移動** | **✕** |

> 上は最初の報告時の観測。**その後のビルドでは入った時点で落ちる**ようになり、
> 「＋ コピー」も出なくなった。原因が分かってみれば、どちらも
> **ドラッグがウィンドウに入って `ole32` が呼びに来た瞬間**という同じ 1 点である。

クラッシュの署名は 7 回すべて同一。

```
Faulting module name: unknown
Exception code: 0xc0000409     ← .NET の fail-fast
```

## Expected

落ちないこと。

## Verification（2026-09-02・`0684b2a`）

実機で確認済み。**1 度も落ちない。**

- 1 回のドラッグでウィンドウの上を 12 回移動 × 複数回、出入り 4 往復 — 落ちない
- `%LOCALAPPDATA%\CrashDumps` **0 件**・`error.log` なし
- 受け取りの経路が通った（`DragEnter 読めた=1〜3 件`。**この経路は一度も動いていなかった**）
- ドロップ 12 項目（フォルダ行・複数・ドライブ跨ぎ・Ctrl/Shift・衝突・自動更新・
  分割時の非アクティブペイン）すべて期待どおり
- 起動終了 8 回（`--panes=4` 含む）で残留プロセス 0

> ドラッグ中に画面へ出る「＋ コピー」「→ 移動」の**文字は撮影できていない**。
> Windows 11 はドラッグ中の絵を画面 DC の外で合成するため。
> 効果は `effect=2` とカーソルハンドルの差し替わりで確認した。

## Cause

**OS からアプリのドロップ先への間接呼び出しが、Control Flow Guard に弾かれている。**

確認をお願いしている側で WinDbg を導入していただき、ダンプからスタックが取れた
（`.ecxr; k 30`）。これで確定した。

```
Subcode: 0xa  FAST_FAIL_GUARD_ICALL_CHECK_FAILURE

03 ... ntdll!KiUserExceptionDispatch+0x2e
04 ... 0x00007ff9`bcf060c0                     ← ガードのチェックで即死（ntdll）
05 ... ole32!CPrivDragDrop::PrivDragDrop+0x183 [com\ole32\com\rot\getif.cxx @ 716]
06 ... rpcrt4!Invoke+0x73
07 ... rpcrt4!Ndr64StubWorker+0x6ee
08 ... rpcrt4!NdrStubCall3+0xc0
09 ... combase!CStdStubBuffer_Invoke+0x7d
```

**アプリのコードは 1 命令も乗っていない。**`ole32` がドロップ先を呼ぼうとした、
その間接呼び出しが弾かれている。ドラッグ元は別プロセス（エクスプローラー）なので、
呼び出しは RPC のスタブ経由で入ってくる。

これで観測がすべて説明できる。

| 観測 | 説明 |
|---|---|
| `RegisterDragDrop` は `S_OK` | 登録は成功する。呼ばれるまで問題が出ない |
| ドラッグがウィンドウの上に来たときだけ落ちる | そのとき初めて `ole32` が呼びに来る |
| **`DragEnter` の入口ログすら出ない** | 呼び出しが成立していない。C# に入る前 |
| `error.log` が出ない | マネージドの外どころか、呼び出しの手前 |
| fault offset が 4 ビルドで同一 | 同じガードのチェック処理。**アプリ側のコードではない** |

### 飛び先がイメージの外にあった

確認をお願いしている成果物（`ExtendExprorer-win32-x64` の exe・3,509,248 bytes）を
Linux 側に落として PE ヘッダを読んだ。

```
DllCharacteristics   = 0x8160        GUARD_CF (0x4000) は立っていない
GuardFlags           = 0x00000100    CF_INSTRUMENTED
GuardCFCheckFunctionPointer = 0x1402986e0
GuardCFFunctionTable = 0  (count=0)  ← 正当な飛び先の表が空
```

`GUARD_CF` が立っていないイメージは、読み込み時に**全体が「正当な飛び先」として
登録される**（旧来の DLL と共存するための仕組み）。つまり**イメージの中の
アドレスなら通るはず**。それでも弾かれたということは、
**飛び先がイメージの中に無かった**ということ。

**裏付け**: このアプリのウィンドウプロシージャは、まさに「USER32 からアプリの
`[UnmanagedCallersOnly]` の静的メソッドへの間接呼び出し」であり、起動から終了まで
成功し続けている。イメージの中が弾かれるならそもそも起動しない。

> `GuardFlags` に `CF_INSTRUMENTED` が立っていながら `GuardCFFunctionTable` が空、
> という組み合わせは中途半端で、**いまも説明が付いていない。**
> 弾かれた飛び先（`rax`）を見れば決まるはずだったが、**修正後は落ちなくなったので
> その観測は取れていない。**修正はこの点の決着に依存していないため、
> **未解決のまま置く。**もっともらしい説明を後から書き足さないこと。

修正の時点では候補が 2 つあり、症状はどちらでも同一だった
（`FAST_FAIL_GUARD_ICALL_CHECK_FAILURE`・同じ fault offset・`RegisterDragDrop` は成功）。

- **(a) 関数表の飛び先がイメージの外**。ソース生成（`[GeneratedComClass]`）に
  任せた関数表の中身が、イメージ内の静的メソッドではなかった
- **(b) 関数表が解放済み**。`ComWrappers` が持つ関数表の領域が先に解放され、
  そこから読んだポインタがゴミだった（＝未割り当てのアドレスへの間接呼び出し）

### 決着: **(a) だった**

登録直後の参照数を出すようにしたところ、**20 回の登録すべてで `参照数=2`**
（`--diag` 4 回・`--diag --panes=4` 4 回。4 分割のときはきっちり 4 行）。
**`RegisterDragDrop` は参照を 1 つ取る。**

これを逆から読むと、**(b) は 4 回目（`129f9f2`）の時点でも起こりえなかった。**
登録に成功したあとに参照を 1 つ返しても、OLE の 1 つが残るので生きている。
つまり落ちなくなったのは 4 回目の**関数表の組み直しの側**であり、
原因は **(a)＝飛び先がイメージの外にあったこと**で確定する。

## Fix

原因が (a) か (b) か外から見分けが付かなかったので、**まず両方を潰し、
そのうえで見分けの付く数字（登録直後の参照数）を出した。**

### 4 回目（`129f9f2`）— 関数表を自前で組む【これが効いた】

`[GeneratedComClass]` / `ComWrappers` をやめ、`IDropTarget` の関数表を手で並べる。
中身は `[UnmanagedCallersOnly(CallConvs = [typeof(CallConvStdcall)])]` の静的メソッド
——**確実にイメージの中にあるアドレス**。関数表は 1 つだけ作って使い回し、解放しない。

`IDataObject` 側の `[GeneratedComInterface]` も落とした（`GetData` を関数表から直に呼ぶ）。
座標は `POINTL` ではなく `ulong` で受けて自分でほどく形をそのまま残している。

### 5 回目（`0684b2a`）— 寿命の綱渡りをやめ、参照数を出す

4 回目には (b) の形がそのまま残っていた。`RegisterDragDrop` のあとに参照を 1 つ返す
書き方だったので、**OLE が参照を取っていなければその時点で解放される**。
そうなればドラッグが来たときに解放済みの関数表を呼ばれる——(a) と区別が付かない。

- 登録直後の**参照数をそのまま `diag.log` に出す**（`2` なら OLE が取っている）
- 成功したら**手放さない**。一覧 1 つにつき 1 個・ウィンドウと同じ寿命
- 参照数を `Interlocked` で数える。別プロセスからの呼び出しは RPC のスレッドで
  入るため、素の `++` では数え損ねる。数え損ねれば同じ症状になる

### 6 回目 — 切り分け用の簡略化を戻す

「成功したら手放さない」は**切り分けのために意図して入れた簡略化**だった。
そのままだと `RevokeDragDrop` のあとも参照が 1 つ残り、`NativeObject`・`GCHandle`・
`ListDropTarget`（ペインを掴んでいる `Func<>` ごと）がプロセスの終わりまで残る。
第 4d 段は**「ペインを閉じる」と メモリ実測 #2d が同時に来る**ので、
ペインあたりの残留があると #2d で説明の付かない増え方として現れる。

参照数が 2 と実測できたので、**登録に成功したらこちらの 1 つを返す形に戻した。**
残る 1 つは `RevokeDragDrop` で返る。

- `diag.log` の数字は**返したあと**の値に変えた。**`参照数=1` が正常。**
  返す前の値を出したままだと、戻し損ねてもログが同じに見えてしまう
- 万一 `RegisterDragDrop` が参照を取っていなかった場合（実測では起きていない）は
  **返さない**。返した瞬間に OLE の側へ宙に浮いたポインタが残るため

`Interlocked` はそのまま残す。**別プロセスからの呼び出しは RPC のスレッドで入る**以上、
素の増減は仕組みとして誤りで、どちらの症状に効いたかとは無関係に正しい形である。

- **Commit**: `129f9f2`（原因の修正）, `0684b2a`（切り分け）, 6 回目（戻し）

## 学び

- **記録が残らずに落ちるときは、境界の内側を疑い続けない。**
  入口の 1 行を「何よりも先に」置くだけで、内か外かが決まる
- **「入口ログが出ない」という事実は 1 回目の時点で出ていた。**それでも 2 回、
  内側の可能性を潰しにいった。**出ている事実の方を先に使う**
- **`0xc0000409` を「.NET の fail-fast」と決めつけない。**サブコードで意味が変わる。
  `0xa` は CFG の間接呼び出しチェック失敗で、.NET とは無関係
- **推測を往復させるより、スタックを 1 回取る方が速い。**確認側に WinDbg を
  入れていただいた。以後「落ちたらスタックを添える」を既定にする
- **CCW（こちらが実装して OS が呼ぶ）は、RCW とは別物として扱う。**
  第 4d 段の持ち出し（`IDropSource`）でも同じ罠がある。**関数表は自前で組む**
- **症状が同じ原因候補が 2 つあるなら、両方潰したうえで見分けが付く数字を出す。**
  ここでは登録直後の参照数。**その 1 つの数字で (b) が消え、原因が (a) に決まった**
- **切り分けのために入れた簡略化には、戻す期限を書いておく。**ここでは
  「メモリ実測 #2d より前に」。書いていなければ、落ちなくなった時点で忘れる
- **数字を出すなら、戻し損ねが見える位置で出す。**参照を返す**前**の値を出したままだと、
  戻しても戻し損ねてもログが同じに見える。返した**あと**の値に変えた

## Notes

コンテキストメニュー（`ShellContextMenuService`）は RCW（こちらが呼ぶ側）なので
この罠には当たらない。同じプロセス内の呼び出しでもある。
