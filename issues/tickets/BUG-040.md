# BUG-040: 2 ペイン以上だと、同じフォルダを読み直してもアイコンの控えが捨てられない

- **State**: Open（**L-02a は直した。L-02 は未解決**）
- **Reported**: 2026-09-29（コードレビュー指摘 2）
- **Area**: shell-icons（`Services/ShellImageList.cs`・`ViewModels/FileListViewModel.cs`）

## Summary

`ShellImageList.BeginFolder` は「**同じフォルダをもう一度読み込んだとき**だけ控えを捨てる」
ために `_folder` と比べていたが、**`_folder` は static の 1 枠**で、
`BeginFolder` は**ペインごとに**呼ばれる。2 ペインで交互に使うと判定が成り立たない。

## Reproduction

1. 2 ペインに分け、A で `C:\X`、B で `C:\Y` を開く（`C:\X` に `.exe` を置いておく）
2. `C:\X\a.exe` を**別の絵を持つ実行ファイルに差し替える**
3. A で `F5`
4. **古いアイコンが残る**

```
A が C:\X を開く          → _folder = "C:\X"
B が C:\Y へ移動          → _folder = "C:\Y"
A で F5（C:\X の再読込）  → _folder("C:\Y") != "C:\X" なので DropFolder が走らない
```

`[icon]` の行も、**別のペインの計測が混ざった内訳**になる。

## Expected

`F5` したペインのフォルダの控えが捨てられ、絵が引き直されること。

## Cause

**再読込かどうかを、static な 1 枠の状態で判定していた。**
正しく知っているのは呼び出し側（`FileListViewModel.Load`）だけ。

## Fix

`BeginFolder(path, isReload)` にして、呼び出し側から渡す。

★ **`_keepSelectionOnReset` を流用しない。**あれは「選択を引き継ぐか」で、
**タブの切り替えは同じパスでも `false`** を渡してくる。
混ぜると**タブを切り替えただけで控えが捨てられる**ので、
`Load` の中で**素のパス比較**を別に取る。

```csharp
var isReload = string.Equals(Path, targetPath, StringComparison.OrdinalIgnoreCase);
_keepSelectionOnReset = keepSelection ?? isReload;
```

## Notes

## 2026-10-01 の実機確認で分かったこと

**2 つに分かれていた。片方は直り、片方は原因が別だった。**

### ★ 直した: タブを切り替えるたびに控えを捨てていた（L-02a）

同じアプリ・同じ間隔で 2 つの経路を並べた実測。

| 経路 | 5 回の `裏で引いた` |
|---|---|
| フォルダへ入り直す | **0, 0, 0, 0, 0**（控えが効いている） |
| **同じパスの別タブへ切り替える** | **10, 10, 10, 10, 10**（＝ファイル数。毎回引き直し） |

**こちらの直し方が間違っていた。**`isReload` を
**「読み込む直前のパスと、読み込む先のパスが同じか」**で決めていたが、
**同じパスの別タブへ切り替えるのもパスは同じ。**

**読み直しは、呼び出し側が「読み直しだ」と言ったときだけ**にした——
`Load` に `isReload` の引数を足し、**`Refresh()`（`F5` と監視からの全体読み直し）だけ** true を渡す。

> **「パスが同じか」は、2 つの別の問いの答えに使えない。**
> 選択を引き継ぐか（`_keepSelectionOnReset`）には使えるが、読み直しかの判定には使えない。
> **1 つの比較を 2 つの判断に使い回したのが原因。**

- **Fix commit**: （このコミット）

### ★ 未解決: `F5` でも絵が古いまま（L-02）

**アプリの辞書ではなかった。**確認セッションが**同一プロセス内で測っている。**

```
同じプロセス・差し替え前       : 909859304
同じプロセス・差し替えて 15 秒後 : 909859304   <- 変わらない
まっさらな別プロセスで同じパス   : 1073243464   <- 新しい絵
```

**アプリは `F5` でちゃんと引き直している**（`裏で引いた=12`）。
**引き直した先のシェルが古い絵を返している。**
`SHChangeNotify(SHCNE_UPDATEITEM)` を自分で呼んでも自分の控えは消えない（測定済み）。

**ただしエクスプローラーは同じ条件で更新できている**（起動 1 か月のプロセスで、
差し替えたファイルの絵とサイズが新しくなった）。**できないことではない。**

#### ★ 次に測ること（推測で直さない）

**上の数字は「描かれた絵の指紋」で、「アイコン番号」ではない。**
**どちらが古いのかで、直し方が変わる。**

| 差し替えのあとに `iIcon` は | 意味 | 効く手 |
|---|---|---|
| **変わる** | シェルは新しい番号を返している＝**イメージリストの中身**ではなく**こちらの反映**の問題 | 控えの捨て方・描き直し |
| **変わらない** | シェルが**同じ枠**を返している＝その枠の絵が古い | `SHChangeNotify(SHCNE_UPDATEIMAGE)` が効く可能性がある（未測定） |

**この 1 つで分かれる。**それまで機序は書かない
（`docs/win32-migration/dev-notes.md`「推測を 1 往復ぶつけるより、判定材料を 1 往復で採る」）。

#### 影響の見積もり（直す価値の話）

- **起きるのは「アプリを開いたまま `.exe` を別の絵のものに差し替える」ときだけ。**
  アプリを入れ直せば新しい絵になる
- **サイズと更新日時の列は正しく更新される**（あちらは自分の列挙から出しているため）。
  **古いのは絵だけ**
- エクスプローラーに合わせるには、**自分でアイコンを抜き出して自前のイメージリストに持つ**
  形になりうる。それは**メモリ要件（30MB 前後）のために避けた構造そのもの**
  （旧 WinUI 版は項目ごとにビットマップを抱えていて、それが移行の動機だった）

**だから、直す前に上の 1 つを測る。**

## Notes

- **`[icon]` の内訳が 2 ペインで混ざるのは直っていない**（控えと計測が静的なため）。
  **パスも混ざる**と報告されたので、行の中に `直前=` と書いて読み違えないようにした。
  絵の取り違えは起きない（I-08 / I-09 で画素まで確認済み）
