# win32-migration 概要

## 目的・背景

メモリ使用量が「気になる点」から**要件**に格上げされた（2026-08-12・ユーザ指示「コストはかかってよいので
Tablacus 並みを目指してほしい」）。目標は**起動直後 30MB 前後**。

WinUI 3 ではこの目標に届かない。**機能の無い雛形の時点で 114MB** で、これは私たちのコードではなく
XAML / DirectComposition の描画スタックが確保している分である。

2026-08-13 の実測（`spikes/`）で、載せ替え先が決まった。

| 基盤 | ワーキングセット | **コミット（実確保）** |
|------|------------------|------------------------|
| **C# AOT ＋ 素の Win32**（採用） | **25.7MB** | **6.8MB** |
| C# WinForms（JIT） | 52.0MB | 12.3MB |
| WinUI 3（現行・AOT） | 136.2MB | 116.9MB |

決め手はコミットサイズの **17 倍差**。マップ済み DLL の見かけの差ではなく、**実際に確保している
メモリの差**なので、載せ替えれば本当に減る。

## スコープ

### 作るもの

- 素の Win32（`comctl32` / `shell32` を直接呼ぶ）＋ C# Native AOT による UI 層
- 既存の機能をすべて移す（file-list / tabs / pane-split / folder-tree / address-bar /
  context-menu / drag-drop / shortcuts / session / shell-icons）
- 移行後の実測（機能を載せた状態で 30MB 前後に収まるかの確認）

### 作らないもの

- **機能追加はしない。** 移行中は現行の仕様に対する新機能を止める（比較対象がぶれるため）
- WinUI 3 版の性能改善（BUG-016 等）。**設計として新実装で解消する**
- 見た目の再設計。`SysListView32` 等をそのまま使えばエクスプローラーの外観になるので、
  むしろ WinUI を手作業で Win32 風に寄せていた調整が不要になる

## 制約

- 開発環境（Linux）ではビルド・実行ができない。**CI ビルド＋検証セッションでの実機確認**という
  現行の運用をそのまま使う
- 移行が終わるまで**現行の WinUI 3 版を動く状態で残す**（`src/ExtendExprorer`）。
  ユーザーが日常的に使っているため、置き換えは段階的に行う
- Native AOT の制約（リフレクション不可・`partial` 必須等）は現行と同じ。**むしろ緩くなる**
  （XAML と CsWinRT が消えるため、BUG-013 のような WinRT 相互運用の問題が減る）

## 引き継ぐもの / 作り直すもの

| | 内容 |
|---|---|
| **そのまま引き継ぐ** | 仕様書・テストケース・チケット（`docs/` と `issues/`）／シェル相互運用（`IFileOperation`・`IContextMenu`・`SHGetFileInfo`）／`NaturalStringComparer`／session の JSON モデル／自動更新・差分更新・リネーム・ソート等の**ふるまいの規則** |
| **書き直す** | View（XAML と code-behind）／ViewModel の**型**（`Visibility` や `ImageSource` など XAML の型に依存している箇所を外す。ロジックと規則は移植） |
| **不要になる** | `WriteableBitmap` によるアイコン保持（OS のシステムイメージリストを借りる）／`TabStrip` の自作折り返し（Win32 で作り直し）／WinUI 固有の回避策（BUG-011 / 013 / 014 の対処） |

## 完了の定義

1. `docs/explorer/*/test-cases.md` の E2E 項目が、新実装で現行と同等に通る
2. **機能を載せた状態で起動直後 30MB 前後**（実測で確認）
3. ユーザーが日常利用に切り替えて問題が出ない
4. 現行 WinUI 3 版を撤去し、CI とドキュメントを新実装に一本化
