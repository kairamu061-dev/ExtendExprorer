# BUG-035: 「PC」の一覧で、ドライブの改名が始まる

- **State**: Closed（2026-09-17 実機確認）
- **Reported**: 2026-09-15
- **Area**: win32-migration / file-list / `src/ExtendExprorer.Win32/UI/FileListView.cs`

## Summary

「PC」を開いた一覧で、**選択済みのドライブ行をもう一度クリックすると改名の編集欄が開く**。

ドライブはフォルダではないので、名前を変えるなら**ボリュームラベルの書き換え**になる。
**利用者の判断は「できてはダメ」**（2026-09-15）。

## Reproduction

1. ツリーの「PC」をクリックして、一覧をドライブの一覧にする
2. ドライブの行をクリックして選択する
3. 間を空けて**もう一度**同じ行をクリックする

```
[rename] 開始 行=0 名前=Windows (C:) 選択=0..12
[rename] 取り消し 行=0 経過=2140ms フォーカス=0xC50C16 一覧=0x11C0782 ドラッグ=無
```

編集欄 `1194,211-1280,230`、中身は表示名 `Windows (C:)`、文字は全選択。

**確定はさせていない**（`Esc` で閉じた）のでボリュームラベルは変わっていない。

## Expected

「PC」では改名が**始まらない**こと。`Delete` / `Ctrl+C` / `Ctrl+X` / 右クリック /
列ヘッダ / D&D と同じく、**黙って何もしない**。

## Cause

**「PC」でフォルダ前提の操作を止めるとき、改名だけ入れ忘れた。**

止めたのは `SelectedPaths`（コピー・切り取り・削除）・`OnRightClick`・`OnBeginDrag`・
`SetSort`・ドロップ先の登録の 5 か所で、**改名はどれも通らない別の経路**だった。

改名は `LVS_EDITLABELS` が持っている——コントロール自身が「選択済みの行を
もう一度クリック」の間合いを測って `LVN_BEGINLABELEDIT` を上げてくる。
アプリ側の入口（F2・右クリックメニュー・新規作成の直後）を塞いでも、
**コントロールが自分で始める分は止まらない。**

## Fix

**`LVN_BEGINLABELEDIT` の処理で 1 を返して止める。**

入口ごとに塞ぐのではなく**ここ 1 か所**にしたのは、編集が F2 でも 2 回目クリックでも
右クリックメニューでも**同じ通知から始まる**ため。入口を数えて塞ぐと必ずどれか漏れる
——実際、今回は 2 回目クリックだけが通っていた。

あわせて `EndLabelEdit` の改名元を `FileListViewModel.PathOf` に変えた。
「PC」では改名を止めたので通らないが、**「いまのフォルダ＋名前」を仮定する場所を
増やさない**ため（確定させていたら `::drives\Windows (C:)` という path を
シェルに渡していた）。

- **Commit**: `6f98e5b`

## 確認結果（2026-09-17・`6f98e5b`）

**「PC」では 4 経路とも始まらず、普通のフォルダでは 4 経路とも今までどおり始まる。**
通知の側 1 か所で止めたことが、そのまま両方の結果に出ている。

| 入口 | 「PC」で | 普通のフォルダで |
|---|---|---|
| 2 回目クリック（前回通っていた経路） | **止まる** | 動く |
| F2 | **止まる** | 動く |
| 右クリック →「名前の変更」 | メニューごと出ない | 動く |
| 新規作成の直後 | （「PC」に新規作成は無い） | 動く |

- ドライブ名は前後で完全一致（`C:=Windows` / `D:=ローカル ディスク` / `E:=ボリューム`）
- `Ctrl+C` / `Ctrl+X` はクリップボードの番兵が残ったまま。**`FileDropList` も載らない**
  ——前回「クリップボードが変化した」と見えた紛れは、編集欄が開かなくなって消えた
- Tab / Shift+Tab での次の行・前の行への移動も従来どおり

## Notes

- **止める場所を「操作ごと」ではなく「コントロールが上げてくる通知」に置く。**
  同じ形の見落としは、コントロールが自分で始める動き（インプレース編集・
  ドラッグ・ツールチップ等）で繰り返しうる
- 確認セッションが**確定させずに止めた**うえで利用者に判断を仰いでいる。
  ボリュームラベルの書き換えは戻せるとはいえ、**試さない判断が正しい**
- 同じ回で、`Ctrl+C` が効いたように見えたのは**この編集欄から選択テキストが
  拾われていた**ため（`FileDropList` ではない）。改名を止めればその誤解も消える
